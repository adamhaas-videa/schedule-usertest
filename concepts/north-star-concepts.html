Four ways to build the next screen

The design tokens are already settled. #124555 is the primary, the radius is 10px, the status families are the -muted tonal sets. None of that is in question, and none of it changes based on what you pick here.

What isn’t settled is how to decide the things tokens are silent on. Every new screen hits those calls within the first ten minutes, and if they get answered differently each time, the app drifts into four dialects. Below are the same six rows of real work, built four ways — each one a different answer to the same three questions.

Same data, same task, true size. Every specimen shows the identical six patients and the identical job, rendered at the app’s real metrics using the Enamel tokens verbatim. Nothing here is scaled or stylised for the page — what you see is what the screen would measure.

The test case

AutoVerify — a real route in the sidebar with nothing behind it yet. Its job: show the front desk which of today’s patients have insurance problems, before the patient is in the chair. It is the perfect test because it doesn’t exist, so nothing about it is settled by precedent, and because it exercises every axis at once.

Border or shadow?
Does a panel sit flat on the page with a stroke around it, or lift off the ground with a drop shadow? The app currently has 8 shadow usages in total — but that’s a pattern, not a rule, and patterns erode.
How loud is a problem?
A failed verification could be a red dot, a muted rose pill, a tinted row, or a bright badge. All four are defensible. Only one of them can be the house answer.
Denser or airier?
Given spare vertical space, does the screen fit more rows or give the existing rows more room? This one compounds — it decides every list, table, and panel you ever build.

A Never raise your voice

In a tie, take the quieter option. A border rather than a shadow. A tonal fill rather than a saturated one. A 4% tint rather than a colour shift. Problems are stated plainly and once — the screen trusts you to read it rather than shouting to make sure you did. This is closest to what the code already does today.

What this settles, permanently
Border or shadow?→Border. 1.5px. Always.
How loud is a problem?→A muted pill, same weight as “verified”
Denser or airier?→Neither — whatever reads calmest

B Colour is wayfinding, never decoration

In a tie, add colour only if it helps someone find something — their column, their patient, the one row that needs work. Colour is a search tool, so a problem row is tinted end-to-end and the carrier gets its own tone. Anything decorative stays grey. C Light to work in, dark to look in

In a tie, ask whether the surface is for doing or for looking. Task surfaces stay on warm paper. The moment the clinician studies an image — a radiograph, a scanned EOB, a referral letter — the room lights go down and the evidence is the only bright thing on screen. The FMX viewer already does exactly this; this doctrine makes it the law rather than a one-off.

What this settles, permanently
Border or shadow?→Border on light, nothing at all on dark
How loud is a problem?→Quiet on task, absent on evidence
Denser or airier?→Dense to work, spacious to look

What stacks and what conflicts

These aren’t four sealed boxes. Only one can be the tiebreaker — the rule that wins when two of them disagree — but several can coexist as ordinary house habits. Here is the honest read.

A + C
Stack cleanly. They govern different things: A decides how loud a treatment is, C decides which ground it sits on. The app already does both today — quiet light task screens, near-black imaging.
A + B
Tension, resolvable. A says use the quieter treatment; B says make problems findable. They collide exactly at “how loud is an error”. Workable if you rank them: quiet by default, colour when scanning is the actual task.
A + D
Tension, real. Calm usually wants air; density removes it. You can have a screen that is quiet and dense — the operatory grid is — but it takes work every time, and whichever you name as tiebreaker is the one that wins on tired days.
B + D
Stack well. Dense screens need colour more, not less, because there is less room for words. The 12-row table above becomes far more usable with B’s tinting applied.
C alone
Doesn’t settle enough. C is genuinely true of this product, but it only fires on screens that show images. It cannot be the sole tiebreaker, because most screens never hit it. It belongs in the system either way — as a rule, not as the North Star.
What I’d recommend, and why. Name A the tiebreaker and carry C as a standing rule beneath it. A is the doctrine your code has already been following without writing it down — 8 shadows in the whole app, tonal status families, hover as a 4% tint — so adopting it costs nothing and stops the drift. C is too true of this product to leave out, but too narrow to lead. B is worth adding later as a scoped rule for scanning surfaces. D I would not name: the density is already there where it’s needed, and as a stated doctrine it gives every future screen permission to shrink.

How to answer

Pick the letter that should win ties — or tell me the recommendation is right and I’ll take it from there. You can also name a stack (“A leads, C stands, B for lists”), which is what I’d write if you don’t override it. Whatever you choose goes into DESIGN.md as the Creative North Star, and every named rule in the file argues from it.
